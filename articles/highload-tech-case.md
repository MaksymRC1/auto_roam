# PWA замість App Store: архітектура офлайн-first додатку для мандрівників в умовах слабкого роумінгу

Коли перед розробником постає завдання створити мобільний продукт для автомандрівників, перша інтуїтивна думка — писати нативку під iOS та Android або брати React Native / Flutter. 

Однак, аналізуючи специфіку використання travel-сервісу на європейських автобанах, я дійшов висновку, що класична модель App Store / Google Play має критичні недоліки для такого кейсу.

У цій статті я хочу поділитися технічним досвідом створення **[AutoRoam](https://autoroam.com.ua/)** — українського помічника для розрахунку європейських віньєток та транзиту, побудованого за архітектурою **Progressive Web App (PWA)**.

---

## 🛠 Чому ми відмовились від App Store: 3 технічні аргументи

1. **Проблема роумінг-трафіку (Edge / 3G зони):**
   На кордонах між європейськими країнами мобільний інтернет часто перемикається між операторами, швидкість падає до 2G/EDGE, або зв'язок зникає взагалі. Змушувати водія в такий момент завантажувати 50+ МБ з App Store для перевірки ціни віньєтки — це провал UX. PWA вантажить мінімальний HTML/CSS/JS бандл вантажопідйомністю в кілька сотень кілобайт.
2. **Offline-First через Service Workers:**
   Завдяки правильній стратегії кешування (`Cache-First` для статики та довідників ПДР, `Stale-While-Revalidate` для паливних тарифів), додаток залишається на 100% працездатним навіть без підключення до мережі. Користувач може перевірити номери екстрених служб чи правила перетину кордону посеред гірського тунелю.
3. **Continuous Deployment без модераційного ботлнеку:**
   Правила дорожнього руху або тарифи на віньєтки в Європі можуть змінюватися раптово. У нативній розробці випуск термінового хотфіксу може застрягти на рев'ю Apple/Google на 24–72 години. У PWA будь-яка зміна на продакшні моментально потрапляє до клієнтського кешу при наступному зверненні.

---

## ⚙️ Архітектурні рішення та оптимізація продукту

При розробці **AutoRoam** основний фокус був спрямований на Core Web Vitals (LCP, INP, CLS) та чуйність інтерфейсу:

*   **Адаптивний UI та Touch Targets:** Для водія за кермом точність натискання має життєво важливе значення. Усі інтерактивні елементи та кнопки розраховані за гайдлайнами доступності з великими зонами дотику (від 48x48px), а темна тема включається на рівні системних токенів, щоб зменшити споживання батареї OLED-екранів.
*   **Локальна агрегація даних:** Замість постійних важких запитів до бекенду, база правил транзиту, посилань на офіційні платіжні шлюзи віньєток та середні ціни на пальне оптимізована у легкомасштабовані JSON-структури, що парсяться без затримок на клієнті.
*   **Безпека та анти-фішинг:** Одною з головних проблем у Європі є шахрайські сайти, які імітують продаж віньєток з націнкою. В архітектуру закладено жорсткий білий список виключно державних платіжних шлюзів кожної країни.
